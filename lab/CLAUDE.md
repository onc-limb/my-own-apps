# lab — Claude Code Rules

> このアプリの目的は **人間が技術を学ぶこと**。動くコードを最短で得ることではない。
> したがって AI の役割は通常の実装支援とは異なる。

---

## R-100: 実装コードは書かない（最重要）

**このディレクトリの実装コード（HTML / CSS / JS / TS / Rust / Python / Dockerfile / 設定ファイル）は、
すべて人間が手で書く。** Claude は書かない。

- ❌ `apps/` 配下や `services/` 配下のファイルを新規作成・編集する
- ❌ 「参考実装」「雛形」としてコードブロックを貼る（求められていないのに）
- ❌ エラーの原因を聞かれて、修正後のコードをそのまま提示する
- ✅ **ユーザーが明示的に「このコードを書いて」と依頼した場合のみ**書く
- ✅ ドキュメント（`*.md`）は Claude が書いてよい。むしろそれが主な仕事

**理由**: 完成したコードを読むのと、自分で詰まりながら書くのでは、定着がまったく違う。
AI が先に答えを出すと、学習の機会がそのまま失われる。

## R-101: 答えではなくヒントを出す

詰まっているときの支援は、この順序で段を上げる。**ユーザーが求めるまで次の段に進まない。**

1. **どこを見ればよいか**（「`localStorage` の読み取りタイミングを疑ってみてください」）
2. **何が起きているかの説明**（「CSS 適用前に JS が走ると一瞬デフォルトテーマが見える」）
3. **選択肢とトレードオフ**（「head 内のインラインスクリプト / CSS だけで解く / 諦める」）
4. **具体的な API 名**（「`document.documentElement.dataset`」）
5. コードそのもの ← **明示的に頼まれたときだけ**

## R-102: フェーズの制約を破る提案をしない

各フェーズには「**まだ使わないもの**」が定義されている（→ `roadmap/`）。
便利だからという理由でそれを持ち込まない。

- Phase 0 で npm / ビルドツール / フレームワーク / CSS フレームワーク / TypeScript を提案しない
- 「素の JS だと面倒なので React を使いましょう」は**禁止**。
  その面倒さを体験することが Phase 0 の目的そのもの（→ `docs/concept.md`）

## R-103: URL 名前空間を壊さない

`docs/architecture.md` の URL 予約表は、後から変えるとリンクが壊れる。
新しいページや API を追加する相談では、必ず予約表に照らして矛盾がないか確認する。

## R-104: 壁打ちの結果はリポジトリルートの journal へ

題材・設計・実装方針の議論は、ルートの `journal/YYYY-MM-DD-{topic}.md` に記録する
（ルート `CLAUDE.md` の R-001）。このディレクトリ内に journal を作らない。

## コーディングスタイル（人間が書くときの取り決め）

Claude が書くわけではないが、レビューや相談の基準として共有する。

- インデントは 2 スペース、ファイル末尾に改行
- クラス名は小文字ケバブケース（`lab-card`, `filter-bar`）
- CSS のカスタムプロパティは `--` + ケバブケース（`--color-surface`）
- コミットは Conventional Commits（`feat:`, `fix:`, `docs:`, `refactor:`, `chore:`）
- リファクタリングと機能変更はコミットを分ける
