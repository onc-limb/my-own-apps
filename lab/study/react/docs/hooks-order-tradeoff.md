# なぜ hook は「呼び出し順」に縛られるのか — 他フレームワークとの比較

> 出発点の違和感（原文）:
>
> > hook はコンポーネントのトップレベルで記載して、常に同じ順序でというのは、
> > 正直副作用を一箇所にまとめてコードで明示的な処理を記載することを重視していた
> > BE エンジニアとしてはちょっと気持ち悪かったりする。
>
> この違和感は正しい。**React は「ソース上の位置」と「実行時の状態」を暗黙に結びつけている**。
> 隠れた結合であり、React が意図的に払ったコストである。

## 1. まず切り分け: これは「副作用の順序」の話ではない

混ざりやすいので先に分ける。

| 対象 | 順序の縛り | 内容 |
| --- | --- | --- |
| **state の紐づけ** | **あり（強い規約）** | どの `useState` がどの値かを**呼び出し順**で決めている |
| 副作用の実行順 | 宣言順に実行されるが依存しない設計にすべき | `useEffect` は宣言順に走るが、順序に依存した設計は避ける |

気持ち悪さの正体は前者。**「変数の識別子が、名前ではなく位置で決まっている」**こと。
BE で言えば、DI コンテナが型名ではなくコンストラクタ引数の位置だけで解決しているようなもの。

## 2. なぜそうなったか — 原因は「関数が毎回走る」こと

React のコンポーネントは**更新のたびに関数本体が再実行される**。
つまり `const [count, setCount] = useState(0)` は毎回新しく評価される。

すると「この行の `count` は、前回のどの値のことか」を対応づける必要が出る。
候補は 3 つあった。

| 案 | 例 | 問題 |
| --- | --- | --- |
| `this` に持つ（旧 class） | `this.state.count` | `this` の取り回し、ライフサイクルメソッドへの分散、ロジックの再利用が HOC 地獄になる |
| 名前で紐づける | `useState("count", 0)` | 同じ hook を複数使えない / カスタムフックを合成すると名前が衝突する / minify で名前が変わる |
| **位置で紐づける** | `useState(0)` | **順序が崩れると壊れる**（採用された案） |

位置を選んだ見返りが、**カスタムフックがただの関数になる**こと。

```tsx
function useToggle(initial: boolean) {   // ただの関数。特別な登録も名前空間もいらない
  const [on, setOn] = useState(initial);
  return [on, () => setOn((v) => !v)] as const;
}
```

これを何個呼んでも衝突しない。名前で紐づける設計だと、呼ぶ側が毎回ユニークなキーを
与えなければならず、合成のたびにプレフィックス管理が発生する。
**「ロジックを関数として切り出して自由に合成できる」ことと、順序の縛りは同じコインの裏表。**

## 3. 実務ではどう扱われているか

順序の縛りは**静的に落とせる**。実行時の地雷ではなく、lint エラーとして扱うのが前提の規約。

```bash
eslint-plugin-react-hooks   # rules-of-hooks / exhaustive-deps
```

- 条件分岐・ループ・早期 return の中の hook はコミット前に落ちる
- React 本体も個数の変化なら実行時に検出する
  （`Rendered more hooks than during the previous render.`）
- ただし**個数が同じで順序だけ入れ替わるケースは検出できない**（分岐の両側で hook を呼ぶ形）

→ lint なしの React プロジェクトは実質的に未完成、という理解でよい。

## 4. 他のフレームワークはどうか

**結論: 同じ縛りがあるのは React と Preact だけ。**
分かれ目は「**コンポーネント関数が毎回走るか、初回だけか**」。

| | コンポーネント関数が走る回数 | 状態の紐づけ方 | 順序の縛り | 代わりの落とし穴 |
| --- | --- | --- | --- | --- |
| **React** | 更新のたびに**毎回** | 呼び出し順（位置） | **あり** | 古い値を掴むクロージャ、依存配列 |
| **Preact** | 更新のたびに**毎回** | 呼び出し順（位置） | **あり**（React と同一） | React と同じ |
| **Solid** | **初回の 1 回だけ** | 変数そのもの（signal オブジェクト） | **なし** | props の分割代入でリアクティビティが切れる |
| **Vue (Composition)** | `setup()` が**初回の 1 回だけ** | 変数そのもの（ref / reactive） | **なし** | `reactive` の分割代入で切れる、`.value` の付け忘れ |
| **Svelte 5 (runes)** | コンパイラが変換。**1 回** | 変数そのもの（`$state`） | **なし**（宣言位置の制約はある） | コンパイラ前提なので `.svelte` の外では制約あり |
| **Angular (signals)** | クラスのインスタンス | クラスのプロパティ名 | **なし** | DI とライフサイクルの複雑さ |

### Preact — React と完全に同じ

`preact/hooks` は React 互換のために**同じ実装戦略**を取っている
（コンポーネントごとの hook 配列 + インデックスのカーソル）。
順序の規約もエラーの出方も React と同じ。

**つまり Preact に乗り換えても、この気持ち悪さは 1 ミリも解消しない。**
Preact の選定理由はバンドルサイズであって、パラダイムの違いではない。

### Solid — 縛りが存在しない

コンポーネント関数が**初回に 1 回しか走らない**ので、対応づけの問題がそもそも発生しない。
`createSignal` は「signal オブジェクトを作る」だけの、ごく普通の変数宣言になる。

```jsx
function Counter() {
  const [count, setCount] = createSignal(0);   // 1 回しか実行されない
  if (someCondition) {
    const [extra] = createSignal(0);           // 条件分岐の中でも問題ない
  }
  return <button onClick={() => setCount(c => c + 1)}>{count()}</button>;
}
```

その代わり別のルールが来る。

- 値の読み出しは**関数呼び出し**（`count()`）。追跡スコープの中で読まないと購読されない
- **props を分割代入するとリアクティビティが切れる**（props は getter の proxy なので）
  → `splitProps` / `mergeProps` を使う

BE 的な感覚では Solid の方が素直に見えるはず。**「宣言は 1 回、変化は購読で伝わる」**という、
イベント駆動やオブザーバパターンにそのまま対応する構造だから。

### Vue / Svelte / Angular

いずれも「宣言は 1 回きり」なので順序の縛りはない。
Vue は `setup()` が 1 回、Svelte 5 はコンパイラが変換、Angular はクラスのプロパティ。

共通の落とし穴は **「リアクティブな入れ物から値を取り出すと繋がりが切れる」** こと。
React の「順序」に相当する、それぞれの隠れた結合がある。

## 5. トレードオフの整理

| | React / Preact | Solid / Vue / Svelte |
| --- | --- | --- |
| 心理的な自然さ | 「毎回上から実行される」は読みやすい | 「1 回しか走らない JSX が再評価される」は最初戸惑う |
| 隠れた結合 | **hook の呼び出し順** | **リアクティビティの経路**（分割代入で切れる） |
| 静的検査 | eslint で落とせる | 一部は lint・型で落とせるが取りこぼしも |
| 最適化の手間 | `memo` / `useMemo` / `useCallback` が必要 | 原則不要 |
| エコシステム | 圧倒的 | 小さい |

**どちらも「隠れた結合」を持っている。位置で縛るか、購読の経路で縛るかの違い。**
「React だけが変」ではないが、「React の縛りが最も明文化された規約になっている」のは事実。

## 6. この違和感をどう扱うか

- **規約として受け入れ、lint で強制する。** 実行時の地雷ではなく、コンパイル時のエラーに落とす
- **`useState` の羅列が気持ち悪いなら、それは設計のサイン。** state が増えすぎている場合は
  `useReducer` に寄せると、状態遷移が 1 箇所（reducer）に集まって BE 的な見通しになる
- **副作用の集約という観点なら、React も同じ方向を向いている。**
  `useEffect` は「外部システムとの同期の宣言」であって、命令的な手続きの置き場ではない
  （この整理はテーマ 4 で扱う）
