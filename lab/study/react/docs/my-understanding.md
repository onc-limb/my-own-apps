# 私の React 理解メモ

> この文書は教科書ではなく、**自分の言葉で立てた仮説と、その検証結果の記録**。
> 引用（> の部分）はすべて自分が実際に書いた言葉そのまま。
> 判定は ✅ 正しい / △ 半分正しい / ❌ 違う の 3 段階。
>
> 対象範囲: 記述層（JSX）と useState の基本形まで。
> 期間: 2026-09-22 〜 2026-09-23

---

## 0. 出発点 — React とは何をするものだと思っていたか

> JSX で Javascript のコード内に HTML 要素のような記述をした上で、
> ブラウザ上で JS から HTML をレンダリングできるための仕組みを提供している。

**判定: △ 半分正しい。**「JSX が描画する」という所だけがずれていた。

正しくはこう分かれる。

| 自分が 1 つだと思っていたもの | 実際の分担 |
| --- | --- |
| JSX がブラウザに HTML を描く | **JSX = 記述のみ**（ビルド時に関数呼び出しへ変換される） |
| | **描画は React ランタイムの仕事**（Element → Fiber → DOM） |

> JSX で扱うことでのメリットとして、状態管理がしやすくなっていること
> - 画面上のステータス
> - フォームの状態
> - 再レンダリング範囲の設定

**判定: ✅ 挙げた 3 つはどれも実在する論点。** ただし「再レンダリング範囲の設定」は表現がずれていた。
React に「範囲を設定する」API があるわけではなく、
**伝播の規則（親が再レンダリングされれば子も原則再レンダリングされる）を理解して、
構造で絞る**のが実態。

### 抜けていた領域

この時点の理解には、次の 3 つが入っていなかった。**実務の事故はここに集中する。**

- **副作用と外界との接続**（イベント / ref / useEffect / データ取得）
- **実行環境**（CSR / SSR / hydration / Server Components）
- **境界**（ルーティング・通信・スタイリングは React の担当外）

## 1. 学習方針についての自分の判断

### 1-1. 内部の詳細より文法を優先する

> このテーマ A は JSX を JS に変換するときに、どのような JS に変換するか、って感じだよね？
> あまりここに詳しくなるより、React の文法を覚えるほうが優先そうと思った。

**判定: ✅ 妥当。** 変換の詳細（`jsx` / `jsxs`、`@__PURE__`）は業務で使わない。

ただし記述層から**持ち越すべき 2 点**だけは残した。後のテーマで必ず戻ってくる地点だから。

1. `<Foo />` と書いても **関数はまだ実行されていない**（呼ぶタイミングを React が握っている）
2. **Element は毎回捨てられ、Fiber は維持される**（だから state が残る）

この判断の結果、学習順を「文法・API を書けるようになる」主線に組み替えた。
内部の話は各テーマの末尾に「なぜそうなっているか」として必要最小限だけ添える（比率の目安 8:2）。

### 1-2. 技術選定の軸になるか

> 本当に将来的に考えたら、ここの違いを React と Preact と Solid などで
> 比較することで技術選定ができるのかな？

**判定: ✅ なる。ただし軸は「JSX の変換結果」ではなく「更新モデル」。**
変換結果は症状であって原因ではない。

| | 更新モデル | コンポーネント関数が走る回数 | 選定理由になるのは |
| --- | --- | --- | --- |
| React | Element を作り直して差分を取る（VDOM 調停） | 更新のたびに毎回 | エコシステム・人材・RSC |
| Preact | 同じ VDOM モデル。ランタイムが小さい | 更新のたびに毎回 | **バンドルサイズだけ**。パラダイムは同じ |
| Solid | JSX が DOM 生成 + 細粒度購読にコンパイルされる | **初回の 1 回だけ** | 更新性能。`memo` 系が不要になる |

決定的なのは最後の列。Solid ではコンポーネントが 1 回しか走らないので、
React の `memo` / `useMemo` / `useCallback` という**最適化の話題が丸ごと消える**。
逆に hooks の作法（依存配列、古い値を掴むクロージャ）も消える。

→ この比較の実地検証は lab 本体の Phase 1（vanilla / react / signals の 3 実装比較）でやる。
この学習トラックで先取りしない。

## 2. useState の基本形 — 最初に引っかかった所

> count という State を保存する変数と、State を更新する関数が useState によって用意されている
> というのと、button の onClick で setCount 関数で count + 1 をしていることは理解した。

**判定: ✅ ただし「State を保存する変数」がのちに最大の誤解になる。** `count` は保存していない。

### 立てた問い

> なんで変数をそのまま書き換えたら反映されないのに setCount で更新すると count の値が変わるのか。
> この count のスコープがどうなっているのか。
> ポインタとかで参照先を直接更新するなどのグローバル変数的な扱いをしているの？

**答え: ポインタでもグローバル変数でもない。**

1. **`count` は変わっていない。** `const` なので再代入は言語仕様として不可能。
   コンポーネント関数が**もう一度呼ばれて、新しいスコープの `count` が作られている**

   ```
   1 回目の呼び出し ─ スコープ①: const count = 0   ← この onClick は 0 を閉じ込めた
   2 回目の呼び出し ─ スコープ②: const count = 1   ← 別物の関数。1 を閉じ込めている
   ```

2. 値の実体は関数の**外**（Fiber 上の hook）にある。`useState` はそこから読んでいるだけ

3. 直接書き換えが反映されないのは**コピーを渡されたからではない**。
   **React が変数を監視していないから**（Proxy も getter/setter も使っていない）

### 「ポインタ？」という直感は半分当たっていた

**オブジェクトの state は参照が共有されている。** `profile.age += 1` は本当に state に届いている。
届いているのに画面が変わらない。つまり「コピーだから反映されない」のではなく
**「通知がないから反映されない」**。

| 方式 | 変更の検知 | 代表 |
| --- | --- | --- |
| 明示的な通知 | **更新関数が呼ばれたときだけ** | React |
| 自動追跡 | 読み書きを Proxy / signal で捕捉 | Vue, Solid, Svelte 5 |

→ **1-2 で聞いた「技術選定の軸」が、実はここに直結していた。**

## 3. 自分で立てた仮説 5 つの検証

| # | 自分の仮説 | 判定 |
| --- | --- | --- |
| 1 | useState はどのコンポーネントで呼ばれたかを知っている | ✅ ほぼ正しい（主語だけ違う） |
| 2 | `useState(0)` が `useState(1)` に書き換わるイメージ | △ 出力は合うが機構が違う |
| 3 | 同じ関数内で複数更新すると最後の値が使われる | ❌ **違う** |
| 4 | onClick が最後まで走った後にコンポーネント関数が実行される | ✅ 正しい |
| 5 | レンダー中に setState すると無限ループ | ✅ ほぼ正しい（補足 2 点） |

### 仮説 1: 宛先をどう知っているか

> useState ってその関数がどのスコープ（コンポーネント）で呼ばれているかという
> メタ情報を保持しているという理解で良い？
> じゃないと setCount でどのコンポーネントを更新するか
> （コンポーネント関数を再実行するか）を理解して予約することができないよね？

**判定: ✅ 推論は正しい。ただし持ち主が `useState` ではない。**

React はコンポーネント関数を呼ぶ**前**に、モジュールスコープの変数
（`currentlyRenderingFiber`）へ「いまレンダリング中の Fiber」を入れる。
`useState` はそれを読み、**その Fiber と hook を束縛した `setState` を作って返す**
（本物では `dispatchSetState.bind(null, fiber, queue)`）。

> 宛先を知っているのは `useState` ではなく、返ってきた `setCount` 自身

ここから 2 つの実用的な帰結が出る。

- `setCount` **だけ**を `setTimeout` や別モジュールや子に渡しても動く（宛先が焼き込み済み）
- 逆に `useState` は**レンダリング中にしか呼べない**（モジュール変数が空だと宛先が決まらない）

### 仮説 2: 初期値が書き換わるイメージ

> setCount 関数は初期の useState の初期値を適切な値に変更した状態で呼ぶという
> コードの書き換え（と同等の処理）をして、関数処理の実行の最後に
> そのコンポーネント関数の再実行を行っている理解でいい？
>
> だから `const [count, setCount] = useState(0)` でプログラム上記載されているものは、
> +1 ボタンを押したら `useState(1)` というように書き換えられたプログラムが実行されるイメージ。

**判定: △ 結果の予想は当たるが、機構は違う。初期値は書き換わらず、2 回目以降は単に無視される。**

このモデルは 3 か所で破綻する。

| 場面 | 「書き換わる」モデルだと | 実際 |
| --- | --- | --- |
| `useState(() => heavy())` | 書き換え後も関数が渡っている | **初回以降その関数は一度も呼ばれない** |
| 同じ値を渡す | 書き換えて再実行 | `Object.is` で同値なら**再レンダリングを省略** |
| 同じイベントで複数回更新 | 最後の値で上書き | **キューを畳み込む**（→ 仮説 3） |

正しい言い方は「**`useState` は初回だけ引数を使い、2 回目以降は保存済みの値を返す**」。

### 仮説 3: 最後の値が使われる ← ここが違った

> 実際の実行は onClick の関数の実行が最後まで行われた後にコンポーネント関数を実行するから、
> 同じ関数内で複数更新をすると、最後の値が使われるということ？

**判定: ❌ 違う。積まれるのは値ではなく「更新の列」。**

| 積んだもの | 畳み込み方 |
| --- | --- |
| 値（`setCount(1)`） | それまでの結果を**上書き** |
| 関数（`setCount(c => c + 1)`） | それまでの結果に**適用** |

ミニ実装での実測:

```
setCount(count + 1) を 3 回     → [値1, 値1, 値1]   → 1     ← 上書きが続いた結果
setCount(c => c + 1) を 3 回    → [関数, 関数, 関数] → 3     ← 3 件すべて適用される
setCount(10); setCount(c=>c+1)  → [値10, 関数]      → 11    ← 混ざっても順に適用
```

**「最後が勝つ」ように見えるのは、値だけを積んだ場合の結果論。**
関数を積めば 3 件とも効く。これが「次の値が今の値に依存するなら関数形式で書く」の根拠。

### 仮説 4: 実行タイミング

（仮説 3 の引用の前半部分）

**判定: ✅ 正しい。** onClick のハンドラが最後まで走り終わってから、
React がキューを畳み込んで関数を再実行する（**自動バッチング**）。途中経過は一度も描画されない。

補足: React 18 以降は `setTimeout` や `fetch().then()` の中でもバッチされる
（17 以前は React のイベントハンドラ内だけだった）。

### 仮説 5: レンダー中の setState

> 上記の考えが合っている場合、setCount などの更新関数を、onClick などの
> ユーザー操作起因の処理じゃなくて、コンポーネント関数で直接実行される位置で
> 実行してしまうと無限にレンダリングが繰り返されるようになってしまう？

**判定: ✅ ほぼ正しい。補足 2 点。**

**(a) 無限には回らない。** React は再レンダリングを **25 回**で打ち切り、
`Too many re-renders. React limits the number of renders to prevent an infinite loop.` を投げる。
ブラウザは固まらない。

**(b) 条件付きなら React は公式に許している。**

```tsx
if (items !== prev) {   // 条件を抜ければ積まれなくなるので収束する
  setPrev(items);
  setSelected(null);
}
```

props の変化に合わせて state を調整する用途。この場合 React は
**DOM に反映する前に**レンダーし直すので、中間状態は画面に出ない。

> 実務で遭遇するループはこの形より、**`useEffect` の中で無条件に `setState` して
> 依存配列を書き忘れる**形が圧倒的に多い（こちらは一度コミットされてから再実行されるのでちらつく）。

## 4. 中間まとめと、そこから出た最後の問い

> レンダリングのタイミングで実行されるコンポーネント関数と、
> ユーザー起因で発火するイベント関数のタイミングの違いを意識した上で、
> setState 関数は更新の列をためて、再レンダリング時に順番に実行しているという理解。

**判定: ✅ 正確。** 1 点だけ精密化すると、畳み込むのは「再レンダリング時」というより
**「再レンダリングの直前〜最中」**（本物は再レンダリング中に `useState` が呼ばれた時点で畳み込む）。

> useState が 2 回目以降無視される。ということは、そのレンダリングが 1 回目なのか
> 2 回目以降なのかをプログラムが理解しているということですよね？
> それはどこで誰がどうやって管理しているの

**答え: 回数は数えていない。`useState` の実装そのものが毎回差し替わっている。**

本物の `useState` はこれだけで、中身を持っていない。

```js
function useState(initialState) {
  const dispatcher = resolveDispatcher();   // ← いま有効な実装を取ってくるだけ
  return dispatcher.useState(initialState);
}
```

| 状況 | 入る dispatcher | 実体 | 初期値 |
| --- | --- | --- | --- |
| 初回レンダリング | `HooksDispatcherOnMount` | `mountState` — hook を**作る** | **使う** |
| 2 回目以降 | `HooksDispatcherOnUpdate` | `updateState` — hook を**読む** | 受け取るが**捨てる** |
| レンダリング外 | `ContextOnlyDispatcher` | 例外を投げる | — |

- **どこで**: `ReactCurrentDispatcher.current`（React のモジュールスコープ変数）
- **誰が**: React 本体。コンポーネント関数を呼ぶ直前と、呼び終わった直後に書き換える
- **どうやって**: その Fiber が一度でもコミットされているか（`current !== null`）で選ぶ

→「2 回目以降は初期値が無視される」の正体は、
**`updateState` が引数を受け取るだけで一度も参照しない**、それだけ。

この設計の副産物が `Invalid hook call. Hooks can only be called inside of the body of a
function component.` という有名なエラー（レンダー終了時に dispatcher を戻すため）。

### 帰結: 順序崩れの 3 パターン

hook の同定は**呼び出し順だけ**。変数名は見ていない。壊れ方は 3 通りで、**1 つは検出できない**。

| 崩れ方 | React の反応 |
| --- | --- |
| hook が**増えた** | `Rendered more hooks than during the previous render.` |
| hook が**減った** | `Rendered fewer hooks than expected.` |
| 個数は同じで**順序だけ入れ替わった** | **エラーにならない。静かに別の値を掴む** |

実測（分岐の両側で `useState` を呼んだ場合）:

```
1 回目 flag=true : branch="A 用の値"
2 回目 flag=false: branch="A 用の値"   ← else 側なのに A の値。例外は出ない
```

→ `eslint-plugin-react-hooks` を必ず入れる。お作法ではなく**強い規約**。

## 5. 現時点で確定した理解（自分の言葉・補正済み）

1. **JSX は記述のみ。描画するのは React ランタイム。** JSX は必ず関数呼び出しに変換される
2. **`count` は State を保存する変数ではない。** そのレンダー限りの `const`。
   値の実体は Fiber 上の hook にあり、`useState` はそこから読んでいるだけ
3. **`setCount` は代入ではなく「再レンダリングの予約」。** 更新をキューに積む
4. **キューはイベントハンドラが終わった後に畳み込まれる**（自動バッチング）。
   値は上書き、関数は適用。だから **関数形式で書けば全部効く**
5. **React は変数を監視していない。** 動く引き金は更新関数の呼び出しだけ。
   だからミューテートは届いていても画面に出ない
6. **初回と 2 回目以降は dispatcher の差し替えで区別される。** 回数は数えていない
7. **hook の同定は呼び出し順のみ。** だからトップレベルで、常に同じ順序で呼ぶ
