# コアコンセプトとエビデンス

## 問題

TypeScript・Node.js・Python・Rust を学びたい。しかし学習には典型的な失敗の形がある。

1. **チュートリアルをなぞって終わる** — 手順は再現できるが、なぜその選択なのかが残らない
2. **フレームワークから始める** — 便利さは得られるが、それが何を解決しているのかが分からない
3. **作って終わる** — 動いた時点で学習が止まり、別の選択肢と比べる機会がない

3 つは同じ根っこを持つ。**「比べる対象がない」** ことだ。
比較対象のない実装は、それが良いのか悪いのかを判断する基準を持たない。

## コアコンセプト

> **同じ機能を複数の言語・実装方式で並べ、切り替えて違いを体感できるサイト**

具体化すると 3 つの軸になる。

| 軸 | 並べるもの | URL での表現 |
| --- | --- | --- |
| フロントの実装方式 | 素の JS / React / Signals | `/labs/<name>-vanilla`, `-react`, `-signals` |
| API の実装言語 | TS Worker / Node / Rust / Python | `/api/ts/*`, `/api/node/*`, `/api/rs/*`, `/api/py/*` |
| 計算エンジン | JS / WASM | `?engine=js` / `?engine=wasm` |

そして **観測基盤（自作アクセス解析）がこの比較の測定装置になる。**
各実装の応答時間・バンドルサイズ・描画時間を記録し、ダッシュボードで並べて見る。
主観的な「速い気がする」を、自分で作った計測系で数字にする。

## エビデンス

このコンセプトは好みではなく、学習科学の知見に沿っている。

### 1. 比較は、単独で学ぶより深い理解を生む

Alfieri, Nokes-Malach & Schunn (2013) は **57 の実験・336 のテスト**を対象にメタ分析を行い、
複数のケースを**比較する**学習（case comparison）が広範に効果を持つことを示した。
特に効果が大きいのは、**比較が後続の直接的な説明からの学習を準備する場合**である。

→ 本サイトでは、「同じ機能の 2 実装を並べる」ことがそのまま case comparison になる。
バンドルサイズや応答時間の差という**表層の違い**が、
状態管理やランタイムという**深層の構造**への入口になる。

### 2. 先に問題に気づいてから教わると、転移が良くなる（A Time for Telling）

Schwartz & Bransford (1998) は 3 つの教室実験で、
**対比的なケースを自分で分析してから講義を聞いた学習者**が、
他のどの条件よりも、1 週間後に**新規の問題へ概念を応用できた**ことを示した。
比較によって「問題の次元」に先に気づくと、
形式的な解法を教わる瞬間が「語るべき時（a time for telling）」になる。

→ **これが Phase 0 で素の HTML / CSS / JS から始める理由である。**
素の JS で状態と DOM の二重管理が破綻する感覚を先に味わってから React に触れると、
React が何を解決しているのかが具体的な痛みとして理解できる。
**遠回りではなく、React を深く理解するための最短路。**

逆に言えば、Phase 0 で「面倒だからフレームワークを入れる」のは、
学習設計上もっともやってはいけない選択になる。

## 知見と設計の対応

| 知見 | 本サイトでの具体化 |
| --- | --- |
| 比較は単独学習より効果的（Alfieri 2013） | 同一機能を複数実装で並置し、URL で切り替える |
| 比較は後続の説明からの学習を準備する（Alfieri 2013） | 比較 → 公式ドキュメントを読む、の順序を守る |
| 先に問題の次元に気づくと転移が良い（Schwartz & Bransford 1998） | Phase 0 は素の JS。破綻を体験してから Phase 1 で React |
| 表層の違いから深層構造へ | 計測結果（数字）を入口に、ランタイムの仕組みへ降りる |
| 比較には測定が必要 | 観測基盤（自作アクセス解析）を土台として先に作る |
