# 2026-08-01 agora キックオフ

## プロジェクトの発足

- 題材: USM（ユーザーストーリーマッピング）と ES（イベントストーミング）に特化した
  ホワイトボードアプリ。Miro / FigJam との差別化は
  ①手法特化 ②音声 AI エージェントによる付箋操作 ③成果物のファイル / git 管理。
- 目的は 2 つ: プロダクトを作ること自体と、**チーム開発プロセスの練習**
  （要求分析 → 要件定義 → 設計 → 実装を文書・レビュー付きで通しで経験する）。
- 体制: ユーザーがファーストエンジニア（要件定義から参画）、
  Claude が PM/PMO と作業エンジニアを演じ分ける。

## 決定事項

| 決定 | 理由 |
| --- | --- |
| プロダクト名は **agora** | 「人が集まり議論する広場」の意。既存アプリ（ariadne 等）の命名系統に合う。候補 storming / fusenba / plotline から選択。 |
| 置き場所は `my-own-apps/agora/` | ユーザー指定。個人アプリのモノレポ慣習に従う。 |
| 文書は `agora/docs/` に番号プレフィックス付き Markdown | フェーズ（0x=インセプション, 1x=要求分析, 2x=要件定義, 3x=設計, 4x=実装計画）が一目で分かる。 |
| 知見・指摘は journal、技術判断は ADR（docs/30-architecture.md） | R-001 と整合させつつ、プロセスの学びとプロダクトの判断を分離。 |
| ドッグフーディング: agora 自身の USM を要求分析で作る | 「ファイルベースの成果物管理」という価値仮説を自分たちで最初に検証できる。 |

## プロセス上の知見（練習の学びログ）

- **憲章は PM が書き、エンジニアがレビューする**ところから始めた。
  チーム開発では「最初の文書に誰がレビューで合意したか」がその後の
  スコープ議論の拠り所になるため、承認者を憲章に明記した。
- 文書計画（docs/README.md）に「作成者 / レビュー / ステータス」列を持たせ、
  進捗管理台帳を文書一覧と一体化した。台帳を別に作ると乖離するため。
- スコープの仮置きに「リアルタイム共同編集を MVP に入れるか」を
  リスク（R-1）として明示した。魅力的だが重い機能は、憲章段階で
  リスク登録しておくと要件定義で冷静に判断できる。

## ユーザーからの指示（キックオフ直後）

- **ルール: 上流（要求分析・要件定義）と実装を切り分け、Claude は自発的に実装しない。**
  - なぜ: チーム開発の練習として、上流工程のプロセスと成果物に集中するため。
    実装が混ざると「上流の成果物だけでどこまで合意できるか」が検証できない。
  - どこで効くか: プロトタイプ・事業側説明用のモックも例外ではない。
    「このタイミングでこういうものがあると良い」と合意してからユーザーが都度依頼する。
- **プロセス知見の蓄積は onclimb-cabin 側で行う。**
  - 必要な成果物の種類・タイミング、やり取りの型、障壁の記録を cabin の
    `process-notes/` に貯める。ユーザー自身のプロセス理解と、
    将来の AgentSkill 化（成果物生成 skill 等）の材料にする。
  - 役割分担: industries 側 journal = agora プロジェクトとしての意思決定記録、
    cabin 側 process-notes = プロセス一般の学習素材（自己完結、industries に依存しない）。
