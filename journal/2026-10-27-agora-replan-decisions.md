# 2026-10-27 agora 再計画の方針決定（AI エージェント開発環境への組み込み）

## 背景

- 2026-08-02（要求分析の計画）以降、agora は更新が止まっていた。マイルストーン
  「要求分析完了 2026-08 末」から約 2 か月遅れており、憲章の撤退基準
  「1 フェーズが目標期日の 2 倍以上超過」に当たりうる状態だった。
- 並行して、AI のエージェントに設計の効いたコードを書かせる開発環境を検討していた。
  その中で「ドメインモデル（集約・イベント・用語）をエージェントに渡し、
  コードとの差分を検出する」道具が必要になった。
  - 既存のツール調査では、EventStorming の成果物をそのまま知識にできるもの、
    モデルから集約違反を検査できるものは見つからなかった。
  - Miro の公式 MCP は付箋の読み取りに未対応という報告があった。
- agora の憲章はビジョンの「効果」に「要件と実装の乖離が早期に発見される」を掲げ、
  柱 3 で成果物をテキストファイル・git で持つとしている。この道具と方向が一致する。

## 決定（ファーストエンジニア）

1. **撤退ではなく再計画する。** スコープを広げて仕切り直す（憲章の変更管理で改訂する）。
2. **図とコードの変換・ルール化ツールは agora の CLI として作る。**
   - 中身: ドメインモデルのファイル形式（コンテキスト・集約・エンティティ・イベント・
     コマンド・ポリシー・用語）、コードからの抽出、モデルとコードの差分、
     境界 lint のルール生成、エージェント向けの知識の出力。
   - 理由: ES ボードと、コードから起こすモデルとで、語彙を揃えて同じ場所で育てられる
     （R-3: フォーマットは後から変えにくい、への対策）。
   - 最初はコードの Entity・集約から始め、ES ボードからモデルへの経路は後にする。
3. **agora を独立リポジトリへ切り出す。** 時期は、コード起点のモデル（Phase 1）の実装を始める前。
   - 今は文書だけなので移しやすい。journal（本ファイルを含む `*-agora-*`）の扱いも、切り出しのときに決める。
4. **実装は Claude を積極的に使う。** 「Claude は自発的に実装しない」ルールを改める。
   - なぜ: ツールを早く実用化するため。
   - どこで効くか: 合意済みのスコープ・設計の範囲の実装、プロトタイプ、スパイク。
     上流（目的・スコープ・設計判断）はファーストエンジニアが決める点は変えない。
   - `agora/CLAUDE.md` の体制表と進め方のルール 0 / 4 を更新した。
