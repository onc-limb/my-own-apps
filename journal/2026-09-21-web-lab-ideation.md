# 2026-09-21 言語学習用 公開ウェブアプリ アイデア出し（初回）

TypeScript（フロント / バック）・Python・Rust を **学ぶこと自体を目的**に、Cloudflare 上の
1 ドメインで公開するウェブアプリを作る構想。既存アプリ群（marginalia / week168 等）が
iOS / CLI 中心なのに対し、これは初のウェブ + 多言語のポートフォリオになる。

- **目的は言語の学習**。「あくまで目的は言語の学習。なので既存のサービスの劣化コピーでも問題はない」

  - ユーザーの言葉:「バニラ JS のページで状態管理してみるのと React を使うときの違いとかを試すために

## インフラ方針（提案）

- 単一 Worker で全部やらず、**gateway Worker（静的アセット + ルーティング）+ 用途別 Worker**を
  Service Bindings で束ねる構成。1 ドメインのまま `/api/ts/*`・`/api/rs/*`・`/api/py/*` を並列に置ける。
- フロントは **Vite の MPA（multi-page）ビルド**。ページ単位で entry を分けるので、
  ページごとに「素の TS」「React」「Signals」を選べる = ユーザーの必須要件を満たす。
- 共有 UI は Web Components + CSS 変数にして、バニラ / React 双方から使う（これ自体が題材）。
- リアルタイムは Durable Objects（WebSocket Hibernation）。**SQLite backend の DO は
  Workers Free プランでも使える**ため、無料枠でリアルタイムまで到達できる。
- Queues / Containers は有料（Workers Paid $5/月）が必要 → 後フェーズ扱い。
- Python は Cloudflare Python Workers（Pyodide）が 2026 時点で ASGI/WSGI（FastAPI・Flask・Django）
  対応・uv ワークフロー・メモリスナップショットによる高速コールドスタートまで来ているため、
  **Container を立てずに Worker として同居できる**見込み。

## 追加で出た指示（同日・2回目以降のやり取り）

### 学習の優先度（重要）
- **TS フロントエンド と Node.js がメイン**、Python と Rust は**拡張**。
- → ロードマップは Phase 0〜3 に TS/Node を集中させ、Rust/Python を後半に置く。

### Cloudflare Workers ≠ Node.js という制約を共有
- Workers は workerd ランタイム。`nodejs_compat` で広範な Node API は使えるが、
  **長命プロセス・`worker_threads`・`cluster`・`child_process`・fs ストリームは学べない**。
- Node をどこで動かすかの候補: Cloudflare Tunnel（無料・同一ドメイン同居）/ Vercel 無料枠（ユーザー案）/
  Containers（有料）/ ローカル限定（CLI・バッチ・テストで学ぶ）。
- ユーザーの反応:「vercel の無料枠で公開するのもアリかもと思った」→ 未決。

### 題材の決め方についての指示（設計方針として重要）
ユーザーの言葉:
> 題材ですが、どちらかというと大まかなテーマだけ決めたい。どんな機能をつけるかは、
> どんな技術を学びたいかに依存するから、大きな方向性(何を扱うか)だけ決めて、
> ウェブソケット学びたいからこういう機能をつける。キューイングや並行処理を学びたいから
> こういう機能をつける、状態管理を学びたいから画面をこうするみたいな拡張をしていきたい。
> このように拡張しやすい題材をいくつか考えて欲しい。

- **理由/含意**: 機能セットを先に決め打ちすると、後から学びたい技術が出たときに題材が受け止められない。
  だから決めるべきは「機能一覧」ではなく **「何を扱うドメインか」** だけ。
- → **題材の評価軸は「面白さ」ではなく「技術を受け入れるキャパシティ（器の大きさ）」** になる。
- → 企画資料の `features.md` は確定した機能表ではなく、
  **「学びたい技術 → その題材ではこう足す」という拡張マトリクス**として書くのが正しい形。
- ✅ 「タイピング道場」方向は良さそうとの評価は得たが、**確定ではなく候補の一つ**扱い。

## 題材とインフラの決定（ユーザー判断）

### 決定1: テーマは2層構造
ユーザーの言葉:「T3 を土台に T6 も統合したい。そこに T5 で技術書のコレクション管理ページというのを題材としたい」

- **土台 = 観測基盤**: T3 自作アクセス解析 + T6 外部サイト監視 を**統合**
- **その上のアプリ = T5 技術書コレクション管理**

**T3 と T6 を統合できる根拠（設計上の軸）**: どちらも本質は
「**時系列イベントを集めて・集計して・見せる**」。イベントを
`(timestamp, source, kind, attrs)` の1スキーマに正規化すれば、
`source` が `web`（自サイトのアクセス）か `probe`（外部監視の結果）かの違いだけになる。
→ **収集 → キュー → 集計 → ダッシュボードのパイプラインを1本で2機能ぶん学べる**。
別々の機能として作らないこと。

**T5 との接点**: 技術書コレクションは外部書誌 API（ISBN → 書影・書誌）から
データを取り込むので、**T6 の監視対象に「依存している外部 API」が自然に入る**。
また T3 の計測対象に本棚の各画面が入る。三者が一方向に依存して閉じる。

### 決定2: インフラは Cloudflare Containers（Workers Paid は別プロジェクトで既に契約済み）

- → Pyodide 制約なしの本物の Python、常駐前提の Node（`worker_threads`・`child_process`・
  fs ストリーム・`ws` 自作）、Rust ネイティブバイナリが全部置ける。
  前提だった「Node は Vercel / Tunnel に外出し」は**不要になったので破棄**。
- **重要な制約（設計に効く）**: Container は常駐サーバではなく
  **Durable Object のライフサイクルで起きて寝るプロセス**。`sleepAfter` で idle 停止。
  ディスクはエフェメラル、`linux/amd64` イメージ必須。
  → **インメモリ状態は失われる前提で設計する**（状態は D1 / DO / R2 へ外部化）。
  これ自体が学習テーマになる（コールドスタート、Worker と Container の役割分担）。
- **コスト設計の肝**: Workers Paid に含まれるのは メモリ 25 GiB-hours / vCPU 375分 /
  ディスク 200 GB-hours（月）。**256MiB の `lite` なら約100時間/月が無料枠**。
  常駐させたいものは `lite` + 短い `sleepAfter`、重い集計は Cron で `standard-1` を数分だけ起動。
  lite を24時間常駐させても月 $2 弱なので、いざとなれば許容範囲。
- WebSocket は Container へもプロキシ可能（`fetch()` を使う。`containerFetch()` は不可）。
  → **同じ WebSocket 機能を DO 版と Container の `ws` 自作版の2実装で比較できる**。

### 学習コンセプトとの噛み合わせ（重要）
自作アクセス解析が、**比較実験の測定装置そのもの**になる。
`?impl=ts|rust`・`?engine=js|wasm` の応答時間を自作アナリティクスが記録し、
ダッシュボードで比較できる → 初回に立てたコンセプト
「同じ機能を複数の実装で並べて比べられるサイト」が、土台の T3 によって実際に測定可能になる。
ドッグフーディングの輪が閉じるので、この2層構造は偶然ではなく必然。

## Phase 0 の学習設計（Claude 提案・採用）

**素の JS を 2 段階に分ける**。これが設計の核心。

- **段階 1: テーマ切替** — 状態 1 個・反映先 1 箇所。素の JS で快適に書ける。
  学び: DOM API、`localStorage`、**初期化順序（FOUC）**、OS 設定と明示選択の優先順位。
- **段階 2: Lab の絞り込み**（検索 + タグ複数 + 並び順）— 状態 3 個・反映先が複数
  （カード表示 / 件数 / チップの選択状態 / 空状態 / URL）。
  → **状態を 1 つ変えたら関係する DOM を全部手で直す必要がある**ことを体感する。

**この「破綻の体験」は失敗ではなく Phase 0 の成果**と位置づけた。
Phase 1 で React を入れたときに「React は状態から DOM を導出する道具」という理解が、
抽象的な説明ではなく自分が味わった痛みの解消として入る。

### エビデンス（R-003 / 学習科学）
- Alfieri, Nokes-Malach & Schunn (2013) メタ分析（57 実験・336 テスト）:
  ケース比較は広範に効果があり、**とくに後続の直接的説明からの学習を準備する場合**に効く。
- Schwartz & Bransford (1998) "A Time for Telling": 対比ケースを**自分で分析してから**
  講義を聞いた群が、1 週間後の**新規問題への応用**で他条件を上回った。
- → **Phase 0 で素の JS をやるのは遠回りではなく、React を深く理解するための最短路**という論拠になる。
  逆に Phase 0 でフレームワークを入れるのは学習設計上もっともやってはいけない選択。
- 出典は `stacks/docs/concept.md` に記載。
