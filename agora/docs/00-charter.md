## 1. 背景

この企画の発端は、企画者（satoshi-onga）自身の 2 つのワークショップ経験である。

- 自身がファシリテーターとして主導した**ユーザーストーリーマッピング**
- DDD 勉強会で参加した**イベントストーミングのワークショップ**

いずれの場でも、手法や前提情報の事前共有が難しく、**本当に議論したいことの
手前の部分（手法の説明・進め方の共通理解づくり）に多くの時間を使ってしまった**。
「もっと事前情報の共有を簡単にできたら良いのに」— これがこの企画の出発点である。

この原体験は、課題 P-1（手法理解のばらつきと説明負担）の仮説を裏付ける一次情報である。
また、P-1 の解決状態が想定する「セッション中のガイド」に加えて
「**セッション前の事前共有**」という角度を含んでいる。後者は要求分析フェーズで
検討する要求の種として扱う（2026-08-02 ヒアリングより）。

## 2. 課題

アジャイル開発の上流アクティビティ — ユーザーストーリーマッピング（USM）と
イベントストーミング（ES）— は、Miro や FigJam などの汎用ホワイトボードツールで
行われることが多い。これらは PO・PM・エンジニアなど関係者全員の主体的な参加を
前提とするワークショップだが、汎用ツールの上で行うと次の問題がユーザーに生じている。

各課題は「誰に・何が起きているか」と「解決したと言える状態」を対で定義する。

### P-1: 参加者ごとに手法の理解がばらばらで、説明の負担が大きい

本課題を最重要とする（優先順位はファーストエンジニアの仮説、2026-08-01。
根拠: 毎回のワークショップで全参加者に起きる＝頻度 × 対象人数で最大。
要求分析フェーズで検証する）。

- **起きていること**: USM/ES への理解度はメンバーごとに異なり、ファシリテーターは
  毎回のワークショップで手法の説明と軌道修正（付箋の種類の間違い、配置ルールの逸脱）に
  時間と注意を奪われる。初参加者は「正しくやれているか」が分からず、
  主体的に参加しにくい。汎用ツールのテンプレートはレイアウトの雛形を与えるだけで、
  **セッション中に手法のルールを教えたり守らせたりはしてくれない**。
- **解決したと言える状態**: 手法未経験の参加者が、短い導入だけで正しくワークショップに
  参加できている（例: 初参加者がセッション開始後まもなく、正しい種類の付箋を
  自力で置ける）。ファシリテーターが手法説明・軌道修正に使う時間が目に見えて減っている。

### P-2: 成果物が当日のスナップショットで死ぬ

- **起きていること**: ボードの内容は SaaS 内にロックインされ、開発が進むにつれ
  参照・更新されなくなる。要件と実装が乖離しても差分として気づけず、
  同じワークショップをやり直すことになる。
- **解決したと言える状態**: 成果物がコードと同じリポジトリで更新され続け、
  変更が差分（PR レビュー）として読める。

### P-3: 付箋操作が議論を中断する

- **起きていること**: ファシリテーターが付箋の作成・整列・分類に手を取られ、
  そのあいだ議論が止まる。ボードを操作できる人に発言が偏る。
- **解決したと言える状態**: 付箋操作を口頭で任せられ、ファシリテーターと参加者は
  手を止めずに議論を続けられる。

差別化の柱（§5）との対応: P-1 ↔ 柱 1＋柱 2 のガイド機能、P-2 ↔ 柱 3、P-3 ↔ 柱 2。

## 3. 対象ユーザー

- アジャイル開発チームの **ファシリテーター／PO／テックリード**
- 特に、要件定義・ディスカバリーのワークショップを定期的に実施し、
  その成果物を継続的に参照・更新したいチーム

いずれも仮説であり、詳細なペルソナ・課題仮説は要求分析フェーズで検証・確定する。

## 4. プロダクトビジョン

> **ワークショップの成果物を、コードと同じように育てられるホワイトボード。**

ビジョンは「アウトプット → ユーザーの評価 → 効果」の連鎖で定義する。
フィードバックとして観測できるのは「評価」までだが、その先の「効果」まで
仮説を持つことで、評価指標そのものが目的化することを防ぐ。

- **アウトプット（何を出すか）**: USM / ES に特化したホワイトボード。
  手法の構造をファーストクラスの概念として扱い、音声エージェントが
  操作とガイドを支援し、成果物を人間可読なテキストファイルとして出力する。
- **ユーザーの評価（観測できる変化）**: 「手法の説明をしなくてもワークショップが回る」
  「初参加者が迷わず付箋を置けた」「ワークショップ後も成果物を PR で更新し続けている」
  という声・行動が観測される（課題 P-1〜P-3 の「解決したと言える状態」に対応）。
- **効果（評価の先に得られるもの）**: 成果物が生きた文書になることで、
  要件と実装の乖離が早期に発見される。ワークショップの実施ハードルが下がり、
  ディスカバリー活動とチームの共通理解の維持が習慣になる。

## 5. 差別化の 3 本柱

**比較対象**（何と差別化するのか）:

- **主競合**: Miro / FigJam / Mural 等の汎用ホワイトボード SaaS を
  USM/ES テンプレートで運用する、現在の実務標準のやり方。
- **副競合**: USM 特化 SaaS（StoriesOnBoard、Avion 等）。USM 特化ツールは既に存在する
  ため、**柱 1 単体では差別化にならない**。ES との併合・柱 2・柱 3 の組み合わせで
  差別化する。実際の機能差は要求分析フェーズの競合分析で確認する。
- **代替手段**: 物理付箋＋壁（非デジタル運用）、Markdown / draw.io 等での手書き管理。

柱ごとの比較軸: 柱 1・柱 2 は主競合・代替手段の「ワークショップ運用の負担」に対して、
柱 3 は主競合・副競合の「SaaS ロックイン」に対して優位を主張する。

| # | 特徴 | 内容 |
| --- | --- | --- |
| 1 | **手法特化** | USM と ES の 2 モードに特化。付箋は単なる矩形ではなく、手法上の意味（アクティビティ／タスク／ストーリー、イベント／コマンド／ポリシー／アグリゲート／ホットスポット等）を持つファーストクラスの概念として扱う。 |
| 2 | **音声 AI エージェント** | 「『注文が確定した』というイベントを追加して」「このタスクの下にストーリーを 3 つ切って」のように、音声で付箋操作を依頼できる。ファシリテーターは手を止めずに議論を進められる。 |
| 3 | **ファイルベース管理** | ボードの実体は人間可読なテキストファイル。git で履歴・差分・PR レビューができ、コードと同じリポジトリで管理・共有できる。 |

## 6. ビジネスケース

- **位置づけ**: 社内効率化ツールではなく、**外部向けの商用プロダクト**として開発する。
  根拠: 企画時の「他サービスと異なる特徴として売り出したい」（企画者の意図）。
- **収益モデル仮説**: フリーミアム。無償枠（個人・ローカル利用）＋
  有償枠（チーム共有・音声エージェント）のチーム単位サブスクリプション。
  価格・プラン設計は競合分析を経て要件定義までに具体化する。
- **投資**: 本プロジェクトの投資は開発工数（人件費相当）。練習プロジェクトのため
  金額目標は置かず、**フェーズごとの投入工数を予算として扱い**、超過を投資超過とみなす。
  予算の具体値: 週 4〜6 時間 × 各フェーズ期間（§11 マイルストーン参照）。
- **回収の考え方（演習用の仮想定）**: MVP 公開後、外部の複数チームが実ワークショップで
  継続利用する（初期トラクション指標）→ 有償転換。指標の数値は要求分析で仮置きする。

## 7. スコープ境界

この節の役割は機能一覧の先取りではなく、**プロジェクトの境界 — 特に「やらないこと」—
の合意**である。機能レベルの取捨は要件定義で行う。

**境界の内側**: USM ボード、ES ボード、付箋の CRUD と手法固有のレイアウト、
ボードのファイル保存／読み込み、音声エージェントによる付箋操作。

**境界の外側（やらないこと）**: 汎用図形描画、USM/ES 以外のフレームワーク対応、
大規模同時編集のスケーラビリティ、モバイル対応。

※ リアルタイム共同編集は魅力的だが実装コストが大きい。MVP に含めるかは
要件定義時のリスク評価で判断する（→ リスク R-1）。

## 8. 成功基準

成功基準はプロジェクトの**アウトカム**で定義する。文書などの中間成果物の完成は
マイルストーン（完了の定義）であって成功基準（成功の定義）ではないため、含めない。

1. **プロダクト**: 課題 P-1〜P-3 の「解決したと言える状態」（§2 で定義）が
   プロダクトで検証できていること。MVP では最低限:
   - **P-1**: USM/ES を知らない人が、ツールのガイドだけを頼りに正しい種類の付箋を
     置ける（ドッグフーディングまたは第三者に触ってもらって確認）。
   - **P-2**: ボードをテキストファイルとして保存し、git で差分が読める。
2. **ビジネス**: 投資（フェーズごとの投入工数予算、§6）が予算内に収まり、
   初期トラクション指標（外部チームでの実利用、数値は要求分析で仮置き）に
   到達していること。
3. **練習**: チーム開発のプロセス — 文書化、レビュー、役割分担、意思決定の記録 — を
   一通り経験し、知見が journal に蓄積されていること
   （本プロジェクトの明示された目的の一つであるため成功基準に含める）。

**撤退基準**（成功基準の裏面 — どうなったら中止を判断するか）:

- 1 つのフェーズが目標期日（§11）を 2 倍以上超過し、完了の見込みも立たないとき。
- P-1 の検証で仮説が棄却され、代わりとなる中核課題（ピボット先）も見いだせないとき。
- 練習目的（成功基準 3）が先に達成され、プロダクト継続の投資対効果が見合わないと
  企画者が判断したとき。

**トレードオフの優先順位**（遅延・想定外が起きたとき何から緩めるか）:

緩めてよい順に ①マイルストーン期日 → ②スコープ（MVP 機能の削減）。
**守るもの**: プロダクト品質と練習目的（プロセスの質）。
根拠: 本プロジェクトは商用の納期制約がなく、期限より検証と学習の質を優先する。

## 9. リスク

| # | リスク | 影響 | 対応方針 |
| --- | --- | --- | --- |
| R-1 | リアルタイム共同編集のコストが大きくスコープが肥大する | 納期・完成度 | MVP はローカル single-user + git 共有で成立させる案を要件定義で検討 |
| R-2 | 音声 AI の認識精度・応答速度が体験を損なう | 差別化の柱が崩れる | 早期に技術検証（スパイク）を設計フェーズ前に実施 |
| R-3 | ファイルフォーマット設計を誤ると後から変更しづらい | 保守性・互換性 | フォーマット仕様を要件定義の成果物に含め、レビューを必須にする |
| R-4 | 練習プロジェクトとして中断・自然消滅する | 目的未達 | フェーズごとに完了条件を定め、journal で進捗を可視化する |

## 10. 体制と役割

| 役割 | 担当 | 責務 |
| --- | --- | --- |
| PM / PMO | Claude | 企画、プロセス設計、文書計画、レビュー、進行管理、知見の記録 |
| ファーストエンジニア | satoshi-onga | 要求分析への参加、要件定義の主導、設計・実装の技術判断 |
| 作業エンジニア | Claude | ユーザーが都度依頼した実装作業のみ担当（自発的に実装しない）。PM 役とは成果物レビューで分離する |

**ステークホルダー**: 本プロジェクトでは企画者・スポンサー・ファーストエンジニアを
satoshi-onga が兼務する。利害の衝突は起きない代わりに、レビューの独立性が
下がりやすい点に注意する（だからこそ役割を明示して演じ分ける）。

**PM の権限レベル**: PM はドキュメント計画の改訂とフェーズ内の進行判断を独断で行える。
スコープ境界（§7）・成功基準（§8）・マイルストーン（§11）の変更、および実装の着手は
承認者の合意を必要とする。

## 11. 進め方

インセプション → 要求分析 → 要件定義 → 設計 → 実装（インクリメンタル）。
各フェーズの成果物と作成タイミングは [`docs/README.md`](README.md) のドキュメント計画を参照。

**ドッグフーディング**: agora 自身の要求分析で USM を作る。最初は Markdown /
テキストで手書きし、プロダクトが育ったら agora 自身に取り込む。
これにより「ファイルベースの成果物管理」という自らの価値仮説を最初に検証する。

**マイルストーン概要**（週 4〜6 時間の投入を前提とする。2026-08-02 承認）:

| マイルストーン | 目標 |
| --- | --- |
| 憲章承認・要求分析開始 | 2026-08 上旬 |
| 要求分析完了（ペルソナ・USM・競合分析のレビュー通過） | 2026-08 末 |
| 要件定義完了（要件定義書・ユースケース・ワイヤーフレーム） | 2026-09 末 |
| 設計・スパイク完了（アーキテクチャ・ファイルフォーマット・音声検証） | 2026-10 末 |
| MVP 完成（成功基準 1 の P-1 / P-2 を検証） | 2026-12 末 |

章の並びの原則: **変わりにくいもの（なぜ・誰の・何を）→ 変わりやすいもの
