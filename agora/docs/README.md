## 作成タイミングの原則

1. **フェーズの入口で作り、出口でレビューを通す。** レビュー未通過の文書を
   前提に次フェーズを始めない（手戻りの元）。
2. **要求と要件を分ける。** 要求分析（10 番台）は「何に困っているか」、
   要件定義（20 番台）は「何を作るか」。実現手段の議論が要求分析に混ざったら
   PM が止める。
3. **設計文書は実装と並行して育てる。** 30 番台は最初から完璧を目指さず、
   ADR（意思決定記録）を追記していく方式にする。
4. **文書は全て Markdown、この docs/ 配下、番号プレフィックスでフェーズを表す。**
5. **プロトタイプ / スパイクは「答える問い・タイムボックス・捨てる/残す」を
   決めてから作る。** UI プロトタイプ（捨てる）は要求分析〜要件定義で、
   技術スパイク（捨てる）はリスク特定後すぐ、ウォーキングスケルトン（残す）は
   実装フェーズの最初。いずれも実施は都度依頼制で、結果は 3x 番台に報告を残す。

## 知見・指摘の記録先

- **意思決定・指示・指摘・知見**: リポジトリルートの `journal/YYYY-MM-DD-agora-{topic}.md`
  （my-own-apps の R-001 に従う）。フェーズの区切り・重要な決定・レビュー指摘の直後に記録。
- **技術的な設計判断**: `docs/30-architecture.md` に ADR として記録。
- 使い分け: 「プロセス・チーム運営の学び」は journal、「プロダクトの技術判断」は ADR。
